# FanchmWrt Device Backports

Device support that FanchmWrt does not ship yet, kept here as an optional patch
set. FanchmWrt stays authoritative: a builder uses a native FanchmWrt profile
without downloading or applying this repository, and only falls back to these
patches when the requested profile is absent upstream.

## Layout

- `manifest.json` records which FanchmWrt release the patches were written
  against: `base_commit` is the tagged commit, `ref` the release tag, `branch`
  the builder-side maintenance branch that carries FanchmWrt's private layer, and
  `patch_count` the number of patch files.
- `patches/` holds the series. `scripts/apply.sh` refuses a count mismatch, so
  `patch_count` is regenerated by `scripts/write-manifest.py` instead of being
  edited by hand.
- `scripts/repair-patch-anchors.py` re-reads drifted hunk context from a target
  tree. It never rewrites added or removed lines.
- `scripts/write-manifest.py` records one release baseline and recomputes the
  patch count.

## Applying

```sh
bash ./scripts/apply.sh /path/to/fanchmwrt
```

The checkout needs full history: the series is pinned to one release tag and also
runs on the maintenance branch built on top of it, so `apply.sh` proves the
requested commit descends from that tag before applying anything, and asks for
`git fetch --unshallow` when it cannot.

A descendant is not a guarantee that the context still matches, so on that path
only, bounded fuzz (1–3 lines) is allowed and each loosened patch is reported.
On the pinned tag the match stays exact. Any failure rolls the whole series back,
and a tree left with `.rej`/`.orig` files is rolled back and refused.

## Following upstream

```text
.github/workflows/follow-upstream.yml
```

Runs daily and can be dispatched for a specific tag. It resolves the newest
release tag, re-tries the current patch set on it (exact match first, then the
same bounded fuzz `apply.sh` allows, then `repair-patch-anchors.py`), and only
publishes when the whole series applies. A release that cannot be followed fails
the run instead of producing a half-working branch.

On success it publishes **two** refs at the same commit:

- `v<version>` — the ref a builder selects explicitly;
- the default branch — the fallback a builder uses when the per-release ref is
  missing, and the ref whose `manifest.json` the builder validates.

Both are needed: a stale default branch names an older base, and the builder's
fallback path then refuses the build even though the release branch is current.
When patches had to be re-anchored, an open pull request documents the change.

## Ref naming

Release refs are named after the upstream tag (`v25.12.6`), never after the
builder's maintenance branch (`fanchmwrt-25.12.6`). The builder derives the tag
from its own selection before asking for a ref here.
